# Design: Product-controlled Complete Access SDO

## Boundary And Ownership

The core owns the protocol-level access mode and request validation. Cfggen
owns the trust-boundary join between ESI capability and product authorization.
The generated product contract carries both facts independently, and
`esop-product-config` reconstructs a core policy only after validating them.

```text
ESI CoE capability + product manifest authorization
    -> cfggen validation and generated artifacts/hashes
    -> product runtime anti-tamper validation
    -> SdoAccessPolicy
    -> SdoTransfer request admission and wire encoding
```

## Core Contract

Introduce:

```rust
pub enum SdoAccess {
    Single,
    Complete,
}

pub struct SdoAccessPolicy {
    complete_access: bool,
}
```

`SdoAccessPolicy` defaults to Complete Access disabled. `SdoTransfer::new()`
keeps that default, while a policy-aware constructor binds generated authority.
Upload/download start methods accept `SdoAccess`, validate policy and subindex,
and mutate the FSM only after validation succeeds.

Complete Access is valid only for subindex 0 or 1. The initiate request sets
bit `0x10`, producing the normal command specifier plus that bit. Segment
commands remain unchanged. Initiate-upload responses expose the response's
Complete Access bit so the FSM can reject a mismatch. Initiate-download keeps
accepting `0x60`; it does not require the bit to be echoed.

Typed errors distinguish disabled policy, invalid Complete Access subindex, and
response mismatch from existing mailbox, object, sequence, and abort errors.

## ESI And Product Contract

Only a direct `Device/Mailbox/CoE` element may provide the ESI capability:

```xml
<CoE CompleteAccess="true"/>
```

An absent attribute means unsupported. Existing strict boolean parsing handles
accepted spellings and rejects malformed values.

The strict per-slave product schema gains:

```json
"coe": {
  "complete_access": true
}
```

An absent object or field means disabled. Cfggen rejects product enablement
when ESI support is false. Product disablement remains valid even when ESI
support is true, preserving product-level control.

Every generated slave stores separate `supported` and `enabled` booleans. They
participate in ESI semantic identity, configuration identity, normalized
product output, inventory, C/Rust output, and robot build input. This prevents
an artifact or cache boundary from silently losing the policy.

## Runtime Validation

`ProductSlaveConfig` retains the two generated booleans. Product validation
checks `enabled => supported` anywhere the generated slave contract is accepted
and exposes a per-position typed `SdoAccessPolicy` only from validated data.
Activation performs the same invariant check, so direct mutation of generated
Rust static data fails before lifecycle release.

The generated policy is authorization, not proof of slave behavior. A slave
that advertises support can still return a normal SDO abort; existing abort
handling remains authoritative.

## Compatibility

- `SdoTransfer::new()` stays fail-closed and ordinary SDO callers use
  `SdoAccess::Single`.
- PDO assignment/mapping explicitly stays on `Single` and receives no new
  product-driven grouping behavior.
- Products without `coe` declarations retain current behavior and generated
  policy values of false.
- Mailbox retry, status polling, segmentation, and abort handling are unchanged
  except for typed access-mode admission and upload response verification.

## Verification

- Core unit tests assert exact initiate bytes, admission failures, response
  matching, `0x60` download acceptance, and unchanged segment commands.
- Mailbox/master integration tests assert the exact transmitted request.
- ESI/cfggen tests cover absent, true, malformed, enabled, disabled, and
  unsupported-enable cases plus hash/artifact changes.
- Product tests cover policy lookup and generated-data tamper rejection.
- Existing generated goldens are regenerated by the repository tooling.

## Rollback

The manifest field is optional and defaults false. Reverting the generated
fields and typed Complete Access path returns all products to single-subindex
SDO access without changing PDO layout, mailbox memory, or cyclic scheduling.
